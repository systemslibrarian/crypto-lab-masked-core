9. Masked Core

crypto-lab-masked-core · COUNTERMEASURES (16th category, selected)

Thesis. The catalog already teaches defenses in several places — Nonce Guard's misuse resistance, Downgrade Wire's transcript binding, Timing Side-Channel's constant-time compare, KEM Trap's key confirmation, Protocol Compose's Encrypt-then-MAC. What it has never done is make a countermeasure itself the object under measurement, and then break it. Revision 1 claimed no lab in 175 teaches a defense; that was simply false and is corrected here.

Construction. First-order Boolean masking of AES-128. Every intermediate x carried as x ⊕ m. Linear layers commute with the mask; the S-box does not, so a masked S-box via table recomputation. Simulated traces, real statistics — same honest framing as Power Trace, whose CPA machinery this reuses directly.

Acts
Unprotected baseline. CPA against plain AES. A key byte falls out in a few hundred traces, with a clear correlation peak.
Masking on. Same attack. Under this idealized fresh-mask, first-order leakage model, increasing the trace count does not make first-order CPA converge on the key — the leakage of x ⊕ m is independent of x. State the model on the page, persistently. Real masked implementations leak through glitches, coupling, transitions, and imperfect randomness, and acts 4 and 5 are where that gets said.
Second-order attack — the climax. Combine two leakage samples (the mask and the masked value) with a centered-product combining function. The key comes back out. It costs far more traces; it is not prevented. Plot traces-required against masking order.
Mask reuse trap — freeze the mask across traces, not within one. Revision 2 said to reuse one mask across S-box lookups inside an encryption and promised first-order CPA would work again. That overclaims: low-randomness masking can remain first-order secure, and the attacks that do succeed against within-trace reuse tend to be horizontal, collision-based, or second-order. The clean fixture is a mask frozen to one constant across every encryption. Fresh randomization is then gone entirely and the masked intermediate is a deterministic function of the unmasked one. Pin the fixture; do not leave the constant arbitrary. Under a Hamming-weight leakage model the correlation recovered depends on the mask value — a balanced constant can suppress or invert the HW correlation and make the attack look like it failed when the protection is in fact gone. Two acceptable resolutions, and the lab should state which it took: fix a deterministic low-Hamming-weight constant and record the predicted correlation in CLAIMS.yaml, or use a single-bit / bit-level first-order distinguisher, which recovers the key for any fixed mask up to a sign flip and removes the dependence on which constant you happened to choose. The second is more robust for a teaching exhibit; the first makes the mask's role more visible. The lesson is unchanged either way: broken randomness collapses the protection while the countermeasure remains intact on paper. Optional Full-lab extension: keep within-trace reuse and demonstrate the horizontal/collision attack it actually invites — but label it as such rather than calling it plain CPA.
Glitch note. State plainly that a scheme proven secure in the probing model can still leak in hardware through glitches, and that this is what threshold implementations exist for. Do not simulate hardware glitches — name what is out of scope.

Negative claim (NEG-1). First-order Boolean masking defeats first-order leakage analysis under the modeled assumptions; it does not protect against higher-order observation. Act 3 proves exactly that sentence and nothing broader. The frozen-mask failure in act 4 is a separate lesson about randomness, not about masking, and CLAIMS.yaml should keep them apart.

CI gate — correcting Revision 1. Revision 1 said to fail the build if the second-order attack stops succeeding. That is a flaky gate; statistical attacks vary run to run and would redden the build on noise. Replace it: fix the PRNG seed, record a traces-to-disclosure band at each order, and fail on band violation rather than on attack outcome. A masked implementation that suddenly resists second-order CPA in this model means the model broke, not that the masking improved — and the band violation is what surfaces that.

Repo description.

Browser demo: CPA pulls an AES key byte from a few hundred traces, first-order Boolean masking flattens it to nothing, then a second-order combining function pulls the same byte back out. Masking is a price, not a wall.
